## Operating Model

Campfire deploys through GitHub Actions only. Render auto-deploy must stay disabled on every API and Web service. Branch flow is:

```text
feature branch -> develop -> main
```

- Feature branches named `###-feature-name` run CI first; after `ci-status` passes, the final CI automation job opens or updates one PR into `develop`.
- PRs into `develop` and `main`, plus pushes to those branches, run `CI`.
- `ci-status` is the only required branch-protection check.
- Successful CI for the current `develop` tip deploys Develop in the same CI run.
- Successful develop deploy and probes create or update one `develop -> main` PR.
- Successful CI for the current `main` tip deploys Production in the same CI run.
- Production uses the protected `production` GitHub Environment before secrets are read or hooks are called.

## Workflow Inventory

| Workflow | File | Trigger | Required result |
| --- | --- | --- | --- |
| CI | `.github/workflows/ci.yml` | PR/push for `develop`, `main`, and `###-*` feature branches | `ci-status` succeeds only when every required validation job succeeds. Feature pushes open/update `develop` PRs; `develop` pushes deploy Develop and open/update promotion PRs; `main` pushes deploy Production. |
| Manual Deploy Develop | `.github/workflows/deploy-develop.yml` | Manual dispatch from `develop` with green `ci-status` for the selected SHA | Preflight, API deploy, Web deploy, probes, promotion PR. |
| Manual Deploy Production | `.github/workflows/deploy-production.yml` | Manual dispatch from `main` with green `ci-status` for the selected SHA | Environment approval, preflight, API deploy, Web deploy, probes. |

## GitHub Secrets And Variables

Set deploy hooks as Environment secrets. Set public URLs as Environment variables.

### `develop` Environment

| Name | Kind | Required | Purpose |
| --- | --- | --- | --- |
| `RENDER_DEVELOP_API_DEPLOY_HOOK` | secret | yes | Render Deploy Hook URL for develop API. |
| `RENDER_DEVELOP_WEB_DEPLOY_HOOK` | secret | yes | Render Deploy Hook URL for develop Web. |
| `DEVELOP_API_URL` | variable | yes | Base API URL, without path. |
| `DEVELOP_WEB_URL` | variable | yes | Frontend URL, without path. |

### `production` Environment

| Name | Kind | Required | Purpose |
| --- | --- | --- | --- |
| `RENDER_PROD_API_DEPLOY_HOOK` | secret | yes, when production exists | Render Deploy Hook URL for production API. |
| `RENDER_PROD_WEB_DEPLOY_HOOK` | secret | yes, when production exists | Render Deploy Hook URL for production Web. |
| `PROD_API_URL` | variable | yes, when production exists | Base API URL, without path. |
| `PROD_WEB_URL` | variable | yes, when production exists | Frontend URL, without path. |

`GITHUB_TOKEN` is built in. The workflows scope it per job. Hook URLs must never be copied into docs, issues, PR comments, or shell history.

## GitHub Environments

Create two environments in GitHub repository settings.

### `develop`

- Deployment branches: selected branches, `develop` only.
- Required reviewers: none.
- Secrets: `RENDER_DEVELOP_API_DEPLOY_HOOK`, `RENDER_DEVELOP_WEB_DEPLOY_HOOK`.
- Variables: `DEVELOP_API_URL`, `DEVELOP_WEB_URL`.

### `production`

- Deployment branches: selected branches, `main` only.
- Required reviewers: at least one maintainer.
- Wait timer: optional.
- Secrets: `RENDER_PROD_API_DEPLOY_HOOK`, `RENDER_PROD_WEB_DEPLOY_HOOK`.
- Variables: `PROD_API_URL`, `PROD_WEB_URL`.

GitHub may request production approval before the preflight job can show missing production values, because Environment secrets and variables are readable only after the environment gate opens.

The deployment workflows keep Environment access in a single deploy-and-probe job per environment. This avoids repeated approval prompts and keeps Environment-scoped secrets available only where hooks and public probe URLs are used.

## Branch Protection

### `develop`

- Require a pull request before merging.
- Require status checks to pass.
- Required check: `ci-status`.
- Block direct pushes.
- Block force pushes.
- Block branch deletion.
- No approval required for solo-maintainer develop merges.

### `main`

- Require a pull request before merging.
- Require status checks to pass.
- Required check: `ci-status`.
- Require at least one approval.
- Require branch up to date before merge.
- Restrict PR source branch to `develop` when repository plan supports it.
- Block direct pushes.
- Block force pushes.
- Block branch deletion.

The CI workflow also fails PRs into `main` when the source branch is not `develop`.

## Render Setup

Prefer creating these services from the root `render.yaml` Blueprint. In Render,
open Blueprints, connect this repository, and select `render.yaml`. The
Blueprint creates the `Campfire` project with `Develop` and `Production`
environments, API/Web services, and Postgres databases.

`autoDeployTrigger: off` is set for every service, so Render does not deploy on
Git pushes by itself. GitHub Actions remains the deploy gate and uses Deploy
Hooks after CI passes.

### Develop

- API service: `campfire-api-dev`.
- Linked branch: `develop`.
- Root directory: `apps/api`.
- Plan: `free`.
- Build command: `uv sync --frozen --no-dev`.
- Start command: `uv run alembic upgrade head && uv run uvicorn campfire_api.main:app --host 0.0.0.0 --port $PORT`.
- Cookie settings: `REFRESH_COOKIE_SECURE=true`, `REFRESH_COOKIE_SAMESITE=none`.
- Web service/static site: `campfire-dev`.
- Linked branch: `develop`.
- Root directory: repository root.
- Build command: `npm ci && npm run build`.
- Publish directory: `apps/web/dist`.
- PostgreSQL: `campfire-db-dev`.
- PostgreSQL major version: `16`.
- API health check path: `/readyz`.

### Production

- API service: `campfire-api-prod`.
- Web service/static site: `campfire-prod`.
- PostgreSQL: `campfire-db-prod`.
- Linked branch: `main`.
- API build command: `uv sync --frozen --no-dev`.
- API pre-deploy command: `uv run alembic upgrade head`.
- API start command: `uv run uvicorn campfire_api.main:app --host 0.0.0.0 --port $PORT`.
- API health check path: `/readyz`.
- Web build command: `npm ci && npm run build`.
- Web publish directory: `apps/web/dist`.
- PostgreSQL major version: `16`.

After the Blueprint sync, for every Render API and Web service:

1. Confirm Auto-Deploy is disabled.
2. Create a Deploy Hook. Deploy Hook URLs are generated by Render and are not stored in `render.yaml`.
3. Store the hook URL only in the matching GitHub Environment secret.
4. Put the public service URL in the matching GitHub Environment variable.

## Migrations

CI validates migrations against ephemeral PostgreSQL:

- `backend-integration-postgres` runs `alembic upgrade head` before integration tests.
- `migrations-contracts` runs `alembic upgrade head`, `alembic current`, `alembic check`, and contract tests.

For live Render databases:

- Develop API stays on Render's free web service plan, so it does not use
  Render Pre-Deploy Command. Instead, its start command runs
  `uv run alembic upgrade head` before `uvicorn`. This is acceptable for
  Develop because the service has a single free instance and migrations fail
  the deploy before `/readyz` can pass.
- Production uses Render Pre-Deploy Command `uv run alembic upgrade head`.

Develop PostgreSQL should use a paid `basic-256mb` instance if it is expected
to persist. Render free PostgreSQL is useful only for disposable experiments.

## Provisioning Production

Production can be unconfigured safely. The workflow fails closed in `preflight` and lists missing names only:

```text
RENDER_PROD_API_DEPLOY_HOOK
RENDER_PROD_WEB_DEPLOY_HOOK
PROD_API_URL
PROD_WEB_URL
```

To enable production:

1. Create production API, Web, and PostgreSQL services in Render.
2. Disable Auto-Deploy on API and Web.
3. Create deploy hooks for API and Web.
4. Add hook URLs as production Environment secrets.
5. Add public URLs as production Environment variables.
6. Confirm production Environment reviewers are configured.
7. Merge a green `develop -> main` PR.

## Manual Redeploy

Use manual redeploy only for a known-good commit already on the target branch. Manual dispatch also verifies that the selected commit has a successful `CI status (aggregate)` check before any Environment job starts. Normal automatic deployments happen inside `.github/workflows/ci.yml`.

### Develop

1. Open `Deploy Develop`.
2. Select `Run workflow`.
3. Choose branch `develop`.
4. Confirm API deploy, Web deploy, and all probes pass.

Dispatching from any other branch fails at `Develop branch guard`.

### Production

1. Open `Deploy Production`.
2. Select `Run workflow`.
3. Choose branch `main`.
4. Approve the `production` Environment gate.
5. Confirm preflight, deploy, and probes pass.

Dispatching from any other branch fails at `Production branch guard`.

## Rollback

Preferred rollback is Git revert plus normal promotion:

1. Revert the bad commit on `develop`.
2. Let CI run.
3. Deploy develop and verify probes.
4. Merge the generated `develop -> main` PR.
5. Approve production deploy.

Emergency rollback:

1. In Render, redeploy the last known-good deploy for the affected service.
2. Open an incident note in the tracking issue or PR.
3. Revert in Git immediately after service is stable.
4. Run normal CI/CD again so Git becomes source of truth.

## Troubleshooting

| Symptom | Check | Fix |
| --- | --- | --- |
| `ci-status` failed | Failed dependency listed in aggregate job. | Open named job logs, fix root failure, push again. |
| Frontend build failed | `Frontend - typecheck and build`. | Run `npm ci && npm run typecheck && npm run build` locally. |
| Backend lint failed | `Backend - lint and typecheck`. | Run `cd apps/api && uv run ruff check src tests scripts`. |
| Mypy warning shown | Non-blocking mypy step. | Track cleanup; does not block merge. |
| Integration failed | PostgreSQL service job. | Check migration, DB URL, test marker, and async fixtures. |
| Migration check failed | `migrations-contracts`. | Create or fix Alembic revision before merge. |
| Deploy hook failed | Deploy job summary shows service and status code. | Confirm Render service exists and hook secret is current. |
| Manual deploy stopped in branch guard | Branch guard could not find green `CI status (aggregate)` for the selected SHA. | Run or rerun `CI` on the target branch, then dispatch deploy again. |
| Probe failed | Probe summary shows first unhealthy URL. | Check Render logs, cold start, migrations, and `*_API_URL`/`*_WEB_URL`. Probes retry for up to 45 attempts with 10-second sleeps. |
| Production preflight failed | Missing names listed. | Add missing production Environment secrets/variables. |
| Promotion PR duplicated | Open PR filters. | Keep source `develop`, target `main`; close stale duplicate manually. |

## Operational Health Checklist

- [ ] Render Auto-Deploy disabled for every API and Web service.
- [ ] GitHub Environments restrict deployment branches.
- [ ] Production Environment has required reviewer.
- [ ] Branch protection requires only `ci-status`.
- [ ] `develop` and `main` block direct pushes and force pushes.
- [ ] Production values are either fully configured or expected to fail preflight.
- [ ] Rollback path has been reviewed before production merge.

## External Setup Still Manual

These settings cannot be committed to the repository and must be confirmed in GitHub or Render:

- GitHub branches `develop` and `main` exist on the remote.
- GitHub branch protection or rulesets match this runbook.
- GitHub Environments and Environment secrets/variables exist.
- Render API/Web/PostgreSQL services exist for each enabled environment.
- Render Auto-Deploy is disabled on API and Web services.
- Develop API start command includes `alembic upgrade head`; Production API uses Render Pre-Deploy Command for migrations.
