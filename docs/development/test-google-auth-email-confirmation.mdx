<p className="cf-kicker">TUTORIAL</p>

This tutorial is for your first local test of the Google sign-in and email-confirmation implementation. It assumes you already know how to start Postgres, the FastAPI API, and the Vite web app.

By the end, you will have:

- a Google OAuth client for local development
- local API env vars for Google OAuth and confirmation codes
- an outbox file containing a real 6-digit confirmation code
- a small set of automated tests that explain what is covered today
- a manual smoke-test checklist for the parts that intentionally touch Google

## What This Feature Adds

The old `/auth/google-stub` path is no longer the normal user path. The app now starts a real backend-owned OAuth flow:

1. The web app calls `POST /auth/google/start`.
2. The API creates a short-lived OAuth flow row, PKCE verifier, nonce, and state cookie.
3. The browser goes to Google.
4. Google redirects back to `http://localhost:8000/auth/google/callback`.
5. The API exchanges the authorization code, verifies the Google ID token, creates or links a Campfire user, sets the normal refresh cookie, and redirects to the web app.

Traditional email/password sign-up now creates an unconfirmed account first:

1. `POST /auth/register` returns `{"status":"confirmation_required"}`.
2. The API writes a confirmation email into the local outbox when `MAIL_BACKEND=console`.
3. `POST /auth/confirm` checks the 6-digit code, confirms the account, and issues the normal session.

## What You Need From Google

You need a Google OAuth 2.0 client ID and client secret. You do not need to enable Gmail, People API, or any app-specific Google API for this local sign-in flow. The app only asks for OpenID Connect identity scopes: `openid email profile`.

Use a sandbox Google Cloud project, separate from any dev or production project.

<Note>
Google's console UI changes over time. The official docs currently describe creating an OAuth client from the Google Cloud Console Clients page, choosing the `Web application` type, and registering authorized redirect URIs. They also call out that the redirect URI must match exactly, including scheme, port, path, and trailing slash.
</Note>

## Create The Google OAuth Client

1. Open the Google Cloud Console.
2. Create or select a sandbox project, for example `campfire-local-yourname`.
3. Open Google Auth Platform or APIs & Services, then configure the OAuth branding or consent screen.
4. Use an external/testing app while working locally.
5. Fill the required app name, support email, and developer contact email.
6. Add yourself as a test user if the app is in testing mode.
7. Create an OAuth client.
8. Choose `Web application`.
9. Add this authorized redirect URI exactly:

```text
http://localhost:8000/auth/google/callback
```

10. Create the client, then copy the Client ID and Client secret.

Store the secret only in your local `.env`. Google may only show the client secret once after creation, so copy it before leaving the page.

## Configure The API Env

Create or update `apps/api/.env` from [apps/api/.env.example](/home/paninit/workspaces/campfire/apps/api/.env.example).

For the new auth feature, these are the important values:

```dotenv
ENV=dev
CORS_ORIGINS=http://localhost:5173
REFRESH_COOKIE_SECURE=false
REFRESH_COOKIE_SAMESITE=lax

GOOGLE_OAUTH_ENABLED=true
GOOGLE_OAUTH_CLIENT_ID=replace-with-client-id.apps.googleusercontent.com
GOOGLE_OAUTH_CLIENT_SECRET=replace-with-client-secret
GOOGLE_OAUTH_REDIRECT_URI=http://localhost:8000/auth/google/callback
WEB_BASE_URL=http://localhost:5173
OAUTH_FLOW_HMAC_KEY=replace-with-local-random-secret

EMAIL_CONFIRMATION_REQUIRED=true
EMAIL_CONFIRMATION_HMAC_KEY=replace-with-local-random-secret
EMAIL_CONFIRMATION_TTL_SECONDS=900
EMAIL_CONFIRMATION_MAX_ATTEMPTS=5
EMAIL_CONFIRMATION_RESEND_COOLDOWN_SECONDS=60
EMAIL_CONFIRMATION_RESEND_HOURLY_CAP=3

MAIL_BACKEND=console
MAIL_FROM=noreply@campfire.local
MAIL_OUTBOX_DIR=tmp/mail

GOOGLE_STUB_ENABLED=false
```

Generate each local HMAC key with:

```bash
python -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

Use a different generated value for `OAUTH_FLOW_HMAC_KEY` and `EMAIL_CONFIRMATION_HMAC_KEY`.

## Verify The Runtime Config

After your usual database migration and API startup, check the public auth config:

```bash
curl http://localhost:8000/auth/config
```

Expected result:

```json
{
  "google": {
    "enabled": true
  },
  "passwordSignUp": true
}
```

If `google.enabled` is `false`, the API did not consider Google fully configured. Check these five values:

- `GOOGLE_OAUTH_ENABLED=true`
- `GOOGLE_OAUTH_CLIENT_ID`
- `GOOGLE_OAUTH_CLIENT_SECRET`
- `GOOGLE_OAUTH_REDIRECT_URI`
- `OAUTH_FLOW_HMAC_KEY`

Then restart the API.

## Run The Focused Automated Tests

Run commands from [apps/api](/home/paninit/workspaces/campfire/apps/api):

```bash
uv sync
uv run pytest -m unit tests/unit/identity/test_start_google_sign_in.py
uv run pytest -m unit tests/unit/identity/test_complete_google_sign_in.py
uv run pytest -m unit tests/unit/identity/test_hmac_code_hasher.py
uv run pytest -m unit tests/unit/identity/test_settings.py
uv run pytest -m contract tests/contract/test_openapi_snapshot.py
```

The current tests cover:

- Google start flow creates a persisted flow and authorization URL
- unsafe `next` redirects are rejected
- Google disabled settings fail as unavailable
- Google callback completion rejects state mismatch and expired flow
- Google happy path creates a user and session using a fake Google provider
- confirmation code HMAC hashing verifies the correct code and rejects a wrong one
- `/auth/config` OpenAPI surface includes the new auth endpoints

You can run the full backend suite with:

```bash
uv run pytest
```

Integration tests use Testcontainers by default. If you prefer your compose database:

```bash
TEST_BACKEND=compose uv run pytest -m integration tests/integration
```

## Know The Current Test Gaps

Some planned tests are not present yet in this implementation. Treat these as manual checklist items until they are added:

- account-linking matrix in `test_account_linking.py`
- full Google OAuth integration test with real Postgres and fake Google provider
- disabled-Google integration fallback test
- confirmation use-case tests for wrong code, expiry, attempts, resend caps, and duplicate sign-up notices
- integration tests for register-unconfirmed, confirm-email, login-blocks-unconfirmed, and confirmation abuse caps
- frontend automated tests; this slice uses manual browser verification plus `npm run typecheck` and `npm run build`

This is important: a successful unit suite does not prove the browser-to-Google round trip works. You still need the manual smoke tests below.

## Smoke-Test Google Sign-Up

1. Open `http://localhost:5173/signup`.
2. Confirm the Google button is visible and enabled.
3. Click the button.
4. Choose the Google account you added as a test user.
5. Accept the consent screen.
6. Confirm the browser lands on `http://localhost:5173/home?auth=ok`, then the app removes the query string after refresh.
7. Reload the page and confirm the session persists through the refresh cookie.

If Google shows `redirect_uri_mismatch`, compare these two values character by character:

- Google Console authorized redirect URI
- `GOOGLE_OAUTH_REDIRECT_URI`

For local dev they must both be:

```text
http://localhost:8000/auth/google/callback
```

## Smoke-Test Google Sign-In

1. Sign out.
2. Open `http://localhost:5173/signin`.
3. Click the Google button again.
4. Use the same Google account.
5. Confirm the app lands on `/home` and does not create a duplicate visible user.

The backend links by Google subject first. If there is no subject link yet, it can link by verified email. If the matching Campfire account was unconfirmed, the Google sign-in confirms it and invalidates pending email confirmations.

## Smoke-Test Email Confirmation

1. Open `http://localhost:5173/signup`.
2. Register with a new local test email and a strong password.
3. Confirm the app navigates to the confirmation page.
4. Open the latest file in [apps/api/tmp/mail](/home/paninit/workspaces/campfire/apps/api/tmp/mail).

Example:

```bash
ls -lt tmp/mail | head
sed -n '1,80p' tmp/mail/<latest-confirmation-file>.txt
```

5. Copy the 6-digit code from the file.
6. Submit it in the browser.
7. Confirm you land on `/home`.
8. Sign out, then sign in with the same email/password to confirm the account is now allowed through.

With `MAIL_BACKEND=console`, the actual code is written to a local file. The API log intentionally only records a redacted `event=mail_sent` line.

## Manual Edge Cases

Use these while the missing integration tests are still being added:

- Enter a wrong confirmation code and confirm the UI shows a generic refusal.
- Enter the wrong code five times and confirm the original code stops working.
- Click resend twice within 60 seconds and confirm the UI/server do not leak whether a cap was hit.
- Try to log in before confirming; correct password should return `confirmation_required`, wrong password should remain a generic credentials failure.
- Set `GOOGLE_OAUTH_ENABLED=false`, restart the API, and confirm `/auth/config` reports Google disabled.
- With Google disabled, confirm password registration and login still work.

## Troubleshooting

| Symptom | Likely Cause | Fix |
| --- | --- | --- |
| Google button missing | `/auth/config` says `google.enabled=false` | Set all Google env vars and restart the API |
| `redirect_uri_mismatch` | Redirect URI differs in Google Console and `.env` | Use exactly `http://localhost:8000/auth/google/callback` |
| Callback redirects to `/signin?auth_error=google_failed` | Missing state cookie, expired flow, bad code exchange, unverified email, or nonce/audience mismatch | Restart the flow from the web button; check API logs for `google_oauth_failure` |
| No confirmation file appears | `MAIL_BACKEND` is not `console`, wrong working directory, or API was not restarted | Set `MAIL_BACKEND=console`, restart API, check `apps/api/tmp/mail` |
| Code always rejected | Old/expired code or wrong HMAC key after restart | Use the newest outbox file; avoid changing `EMAIL_CONFIRMATION_HMAC_KEY` mid-test |
| Integration tests skip | Docker/Testcontainers cannot start Postgres | Use `TEST_BACKEND=compose` with your local test database |
